# web-hva —— 《航海争夺》人机对战网页（地图 A，纯本地、无服务器）

把项目里训练好的策略网络**量化压缩后内联进网页**，做成一个可以像原热座网页那样直接
双击打开的人机对战页面：初始界面选先后手、可随时打开规则说明，AI 的**每一次决策都会
展示出来并至少停 1.2 秒**。

```
双击 index.html 即可开玩 —— 不需要任何服务器、不需要联网、不需要构建步骤。
```

### 1.1 最少需要几个文件？

**一个 html + 三个 js，放在同一个文件夹里就够了**（无子目录、无服务器、无构建、无网络）：

```
你的文件夹/
├─ index.html      ← 双击这个
├─ game.js         ← 引擎（必须先于下面两个被 <script> 载入，见下）
├─ weights.js      ← 量化权重（311 KB，体积都在这里）
└─ ai.js           ← 反量化 + 前向推理
```

* `index.html` 里只有三条相对路径的 `<script src>`，顺序为 `game.js → weights.js → ai.js`
  （`game.js` 挂 `window.CFS`，`weights.js` 挂 `window.CFS_MODEL`，`ai.js` 挂 `window.CFS_AI`；
  三者都在加载时只做定义、不互相调用，所以顺序其实只要保证都在 body 结束前即可）。
* **不能**用 ES module / `fetch`：`file://` 协议下浏览器会以 CORS 为由拒绝加载模块与 fetch，
  所以这里刻意全部用普通 `<script src>` 并把权重直接挂到 `window` 上——这正是"不依赖服务器"的前提。
* 已实测：把上述 4 个文件复制进一个空文件夹（另加一个测试驱动脚本），用 `file://` 打开、
  无头浏览器合成点击**完整打完一局**，页面 0 报错。见 §5.5 `run_clean_folder_test.ps1`。
* `export_weights.py` 与 `verify/` **不是运行必需的**，只是导出工具与验证脚本，删掉不影响游玩。

> 页面**刻意不用 ES module、不用 `fetch`、不用 `import`**：`file://` 下浏览器会以 CORS 为由
> 拒绝模块与 fetch，因此三个脚本都是普通 `<script src>`，权重直接挂到 `window` 上。
> 这也是"不依赖服务器"能成立的前提。

## 2. 玩法与流程（与原热座网页一致的部分）

1. **开局界面**：① 选择 **我先手**（你执玩家 1）或 **AI 先手**（你执玩家 2，AI 执玩家 1）；
   ② 地图固定为 **地图 A**（附 5 列预览）；③ 「📖 游戏规则」按钮弹出规则说明
   （只讲必要规则 + 地图 A 表格，可用 ✕ / 点遮罩 / Esc 关闭）；④ 开始对局。
2. **对局界面**：左右两块棋盘（行 0 在最下，与原网页相同的摆法与图标）、列奖励图标行、
   分数、藏宝图归属、当前行动方高亮、底部对局记录。
3. **你的回合**：抽牌后二选一「保持朝上面放置 / 翻面查看（不可逆）」——选翻面会先把新的一面
   展示给你，再点「放置此方块」确认（与 `index.html` 的交互一致）；然后点击任意高亮的空格选列；
   猴子效果会让你点一个高亮的相邻方块。**你只能看到朝上的一面**，另一面不可见。
4. **AI 的回合**：AI 抽牌、翻面、选列、翻猴子，每个决策点都有一行
   `🤖 AI 决策：…`，写清它做了什么（翻了哪一面、放到第几列、列奖励是什么、翻哪个相邻格），
   并**至少停 1.2 秒**；若这次网络推理本身耗时超过 1.2 秒，就不再额外等待
   （实际推理约 0.4 ms，所以正常情况下都是停满 1.2 秒）。
5. **结算**：角色效果、列奖励、藏宝图 +1、终局计分（瞭望员/木匠/鹦鹉/水手）、
   炮手 ≥3 判负且记 0 分 —— 全部按现行规则实现；结束时给出胜负、终局分数、炮手数、完成列数，
   并提供「再来一局 / 重新选择先后手」。

## 3. 权重压缩

**量化方案**：`per-group 对称 8bit`（`export_weights.py`）

* 只压 2D 权重矩阵；**沿输入维每 128 个数为一组**，每组独立求 `scale = max|w| / 127`，
  存 `round(w/scale)` 到 `[-127, 127]`。组内共用一把 scale ⇒ 组越小越精确、scale 开销越大。
* 偏置与 `value` 头的偏置保持 fp32（全部加起来 550 个数 ≈ 2 KB，压了没意义还伤精度）。
* 输出 `weights.js`：每个张量 = `{shape, g, sc:(base64 fp32 scales), d:(base64 int8)}`。
* **反量化在网页加载时一次性完成**（`ai.js: dequantize()` → `Float32Array`），
  推理全程 fp32，所以推理路径与 torch 的差别**只**来自量化本身。

| 项 | 数值 |
|---|---|
| 参数量 | 228,901（`trunk.0` 256×599、`trunk.2` 256×256、4 个决策头 2/5/4/25、`value`） |
| fp32 原始大小 | 894.1 KB |
| 量化载荷 | 232.4 KB（int8 权重 + fp32 分组 scale） |
| **`weights.js`（base64 后）** | **311.3 KB → 压缩比 2.9×** |
| 相对重建误差 | max 0.0039（7 个矩阵全部）；组大小从 8 到 128 都是 0.0039 |

### 3.1 量化到底损失了多少？（都实测过，不是估计）

**(a) 反事实动作一致率**：让 fp32 策略自己对局，在它遇到的每个**多选**决策点上再问一次
「量化网络会选什么」（`verify/quant_sweep.py`，每组 26,127 个决策点）：

| group | 8 | 16 | 32 | 64 | **128（本页采用）** |
|---|---|---|---|---|---|
| 动作一致率 | 99.80% | 99.76% | 99.54% | 99.49% | **99.41%** |
| `weights.js` 体积 | 449 KB | 375 KB | 338 KB | 320 KB | **311 KB** |

**(b) 头对头胜率**（真正的验收：int8 策略 vs fp32 策略，交替坐先/后手，3000 局）：

| group | int8 vs fp32 胜率 | 判定 |
|---|---|---|
| **128** | **0.4977 ± 0.009**（1491 胜 4 平 1505 负） | 与 0.500 不可区分（z = −0.26） |
| 32 | 0.4957 ± 0.009 | 同上（z = −0.48） |

**结论**：把组从 128 缩到 8（体积 +45%）只把"决策一致率"从 99.41% 抬到 99.80%，
两种配置在 3000 局头对头里都**测不出**相对 fp32 的胜率损失。既然本页的主要目标是压体积，
就直接取最省的 **group = 128**；量化带来的差异（约每局 0.2 个决策）落在噪声里。

## 4. 为什么引擎/特征要用 Python 那一套

AI 是照着 `cfs/encode.py` 的 599 维特征训练的，其中最后 19 维是**牌堆均值场后验**
（`P(背面=r | 正面=T)` 的 8 维、剩余朝上面期望 9 维、期望剩余总数 1 维）。
网页里必须**一模一样**地复现它，否则 AI 会看到它没见过的输入。因此：

* `game.js` 里的 `Game` 用**生成器**复刻 `cfs/engine.py` 的协程结构（鹦鹉嵌套回合、
  猴子连锁翻面都靠 `yield`），决策点协议（flip / col / monkey）与 Python 完全一致；
* `MeanFieldBelief` 是 `cfs/belief.py` 的均值场方案的逐行移植（软移除台账 + 完整对修正）；
* `BeliefDriver` 只从**公共视图序列**推出信念事件（同样不读牌堆），保证没有隐藏信息泄漏；
* 结局与计分按**现行规则**（`boomRule="lose"`：炮手 ≥3 判负且该方记 0 分）。

## 6. 已知取舍

* **只支持地图 A**（按需求）。地图 B/C/D/E/G 的列奖励与囚徒机制在引擎里保留了分支，
  但未实现 G 的囚徒区，遇到会显式抛错而不是静默出错。
* **量化是有损的**：约 0.6% 的决策会与 fp32 网络不同，实测胜率损失 ≤ 2.0pp（3000 局头对头，
  95% 置信上界；点估计 0.23pp），与 fp32 统计不可区分。这是需求里明确接受的代价。
* 牌堆耗尽时按原规则**重建整副新牌堆**（`index.html` 行为）；`jsref` 参考引擎为了对拍
  不重建而是报错，这是两边**已知且有意**的差异（对拍脚本会给足 300 张牌）。
* AI 用确定性 argmax（与训练评估口径一致），不复现采样带来的多样性。

## 7. 修复记录

### 7.1 对局记录的归属错位（2026-10-03 修复）

**现象**：日志里「你抽到…」其实是 AI 抽的，「AI 抽到…」其实是你抽的。

**根因**：引擎的一次 `game.step()` 并不只做"当前玩家的这一步"——它在结束当前回合后
**会继续一路推进到下一位玩家的第一个决策点**（这正是"决策点协议"的设计：调用方只管
一个个送动作）。于是同一批事件里同时包含：

* 当前玩家本步产生的事件（`flip` / `place` / `score` / `monkeyFlip` / …）；
* **下一位玩家的 `draw`**（他刚开始新回合、抽了牌，然后停在 flip 决策点等你/它决策）。

而旧代码是 `flushEvents(view.acting === humanSeat ? 'you' : 'ai')`，把**整批**事件按
"刚刚是谁在行动"打标签 —— 于是下家的抽牌被记到了上家头上。终局更有 `_computeEndScores`
一次性抛出**双方各自**的瞭望员/木匠/鹦鹉/水手计分事件，同样被整批打成了同一个人。

**修复**：归属改为**按事件自带的玩家** `ev.p`（引擎在每个事件里都写了 `p`），
不再依赖"刚才是谁在行动"；同时 `addLog` 拆成 `(who, text, cls)`，让"归属"与"强调样式"
（额外回合/列完成/爆掉）互不干扰。

**量化影响**：`verify/check_log_attribution.mjs` 在同一局里同时按新旧两种规则统计 400 局、
9779 条「抽到」记录 —— 旧规则错归属 **8212 条、出现在 400/400 局**（约 84%，只有鹦鹉额外回合
里同一位玩家接着抽的那部分才是对的），新规则 **0 条**。真浏览器端也加了同样断言。

> 注：这个 bug **只影响对局记录的显示文字**，不影响引擎状态、不影响 AI 决策、不影响胜负与计分
> （归属标签是渲染层的事，引擎事件本来就带正确玩家）。
